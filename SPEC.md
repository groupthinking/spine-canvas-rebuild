## 1. Executive Summary

This document specifies a complete, private rebuild of the Spine Canvas / Swarm product surface: an infinite canvas on which typed blocks are generated by AI agents, wired together as a directed acyclic graph (DAG), and executed as runs that emit real downloadable artifacts (.docx, .xlsx, .pptx, .png, .html). The rebuild targets a single-user deployment.

* **12 POSTGRES TABLES IN CORE DATA MODEL**
* **17 + 5 API BLOCK TYPES + APP-ONLY BLOCK TYPES**
* **4 MODEL PROVIDERS BEHIND ONE ROUTER** OpenAI · Anthropic · Google · OpenRouter
* **15 wks BUILD ENVELOPE ACROSS 4 PHASES** 3 / 4 / 4 / 4

### 1.1 What is being rebuilt
* An infinite canvas workspace where every artifact is a typed block, and every dependency is an explicit edge.
* A run engine that accepts a natural-language prompt plus constraints and materialises a block graph as output.
* A block library spanning 17 API-addressable block types plus 5 app-only container/UI block types (Chat, Frames, Inputs, Folder, Folder Synthesis).
* Swarm Mode: a hierarchical task tree where an L1 conversational orchestrator plans, and lower tiers create and fill blocks.
* A cascading re-run engine invalidating descendants via topological traversal plus Supabase Realtime.
* An outbound integration and MCP layer with OAuth connectors and a first-party MCP server.

### 1.2 What is deliberately out of scope
* Multi-tenant billing, subscription webhooks, and plan upgrade flows.
* Team/workspace sharing, roles, and invitations. RLS is a single-owner predicate.
* Horizontal worker fleets.

Critical grounding caveat: every row in the proposed Postgres schema is flagged confidence = Inferred. Validate column names against live API payloads during Phase 1 before writing migrations that are expensive to reverse.

## 2. System Architecture

### 2.1 Layer Decomposition
The system is a single Next.js 14 App Router application deployed to Vercel, with Supabase providing authentication, Postgres, object storage, and realtime change streams.

**TABLE 1 — ARCHITECTURAL LAYERS AND RESPONSIBILITIES**

| Layer | Implementation | Responsibilities |
| :--- | :--- | :--- |
| Canvas client | React 18 + @xyflow/react + Zustand + Tailwind | Infinite canvas rendering, drag-to-connect, frame grouping |
| Realtime sync | Supabase Realtime (postgres_changes) | Push block status/content updates; trigger invalidation UI |
| API surface | Next.js App Router route handlers | Run creation, block CRUD, artifact signing, webhook dispatch |
| Orchestration | Swarm planner + task dispatcher | Decompose prompts into tasks, enforce allowed_block_types |
| Model router | Vercel AI SDK provider registry | Route block type + agent tier to OpenAI/Anthropic/Google/OpenRouter |
| Generation workers | Serverless + background functions | Per-block-type generators writing to Supabase Storage |
| Data | Supabase Postgres (12 tables) + Storage | Canonical graph state, run history, artifacts |
| Integrations | MCP server + OAuth connectors | GitHub, Google Workspace, web, YouTube |

### 2.2 Run Lifecycle
1. Intake — run created with prompt, template, allowed_block_types, agent_instructions; status = queued.
2. Planning — Swarm planner writes rows to tasks forming the task tree.
3. Materialisation — each leaf task creates a blocks row (status = pending) and edges rows.
4. Execution — dispatcher walks the DAG in topological order, invoking block-type generators.
5. Completion — blocks resolve to completed/failed; run records final_output, credits_consumed, completed_at.
6. Propagation — Realtime broadcasts changes; webhook_deliveries enqueued.

Every AI-generating block type shares a four-state machine: pending, running, completed, failed. Static container blocks (Frames, Inputs, Folder) have no generation lifecycle.

Design rule: the blocks table is the single source of truth for canvas state.

## 3. Postgres / Supabase Data Model

The data model comprises twelve tables grouped into four concerns: identity/access (users, api_keys, integrations), graph state (canvases, blocks, edges, files), execution (runs, run_artifacts, tasks), and egress (webhook_endpoints, webhook_deliveries).

### 3.1 Core Tables

**TABLE 2 — TWELVE-TABLE CORE DATA MODEL (ALL ROWS CONFIDENCE = INFERRED)**

| Table | Columns | Concern |
| :--- | :--- | :--- |
| users | id, email, display_name, plan, monthly_credits, daily_bonus_credits, credit_pack_balance, created_at | Identity |
| api_keys | id, user_id, key_prefix, key_hash, name, revoked_at, created_at | Access |
| integrations | id, user_id, provider, oauth_access_token, oauth_refresh_token, scopes, status, connected_at | Access |
| canvases | id, user_id, name, layout, created_at, updated_at | Graph |
| blocks | id, canvas_id, type, name, status, content, url, config, position, created_at, updated_at | Graph |
| edges | id, canvas_id, source_id, target_id, created_at | Graph |
| files | id, canvas_id, block_id, storage_path, mime_type, size_bytes, created_at | Graph |
| runs | id, canvas_id, user_id, prompt, template, allowed_block_types, agent_instructions, status, final_output, estimated_duration_ms, credits_consumed, started_at, completed_at | Execution |
| run_artifacts | id, run_id, file_url, mime_type, created_at | Execution |
| tasks | id, canvas_id, run_id, parent_task_id, tier, persona, agent_tier, goal, status, block_id, created_at, completed_at | Execution |
| webhook_endpoints | id, user_id, url, secret_hash, subscribed_events, created_at | Egress |
| webhook_deliveries | id, endpoint_id, event_id, event_type, payload, response_status, delivered_at, created_at | Egress |

### 3.2 Column-Level Implementation Notes
* Primary keys: uuid with gen_random_uuid() defaults; timestamptz created_at/updated_at with a shared set_updated_at() trigger.
* blocks.type: a Postgres enum enumerating the 17 API block types. App-only types (Frames, Inputs, Folder) stored with a ui_only flag.
* blocks.content vs blocks.url: content holds inline markdown/JSON output; url holds the signed/public location of a generated artifact. Binary artifacts also get a files row and, inside a run, a run_artifacts row.
* blocks.config: jsonb — per-block-type input schema payload. Deliberately schemaless with per-type Zod validators.
* blocks.position: jsonb of { x, y, width, height }; canvases.layout stores viewport state and frame bounds.
* edges: UNIQUE (canvas_id, source_id, target_id) plus an application-level cycle check — execution requires a DAG.
* runs.allowed_block_types: text[] used as a hard allowlist by the planner.
* tasks: self-referencing parent_task_id forms the Swarm tree; tier/persona/agent_tier indexed.
* Secrets: api_keys stores only key_prefix + key_hash (argon2id); webhook_endpoints stores secret_hash for HMAC verification; integrations OAuth tokens encrypted at rest.

### 3.3 Indexes, RLS, and Realtime

**TABLE 3 — INDEXES, RLS, REALTIME, AND STORAGE LAYOUT**

| Object | Definition | Purpose |
| :--- | :--- | :--- |
| idx_blocks_canvas_status | blocks (canvas_id, status) | Canvas hydration and pending-work scans |
| idx_edges_source / idx_edges_target | edges (source_id) / edges (target_id) | Forward BFS for cascade, reverse lookup for context |
| idx_tasks_run_parent | tasks (run_id, parent_task_id) | Task-tree reconstruction per run |
| idx_runs_canvas_started | runs (canvas_id, started_at DESC) | Run history timeline |
| idx_files_block | files (block_id) | Artifact resolution for download buttons |
| idx_wh_deliveries_endpoint | webhook_deliveries (endpoint_id, created_at DESC) | Delivery log and retry sweep |
| RLS (all tables) | USING (user_id = auth.uid()) joined via canvas_id where absent | Single-owner isolation |
| Realtime publication | supabase_realtime FOR TABLE blocks, runs, tasks | Drives live canvas status and cascade invalidation |
| Storage buckets | artifacts (private), uploads (private) | Signed-URL delivery of files and uploads |
