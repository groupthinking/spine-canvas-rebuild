## 1. Executive Summary

This document specifies a complete, private rebuild of the Spine Canvas / Swarm product surface: an infinite canvas on which typed blocks are generated by AI agents, wired together as a directed acyclic graph (DAG), and executed as runs that emit real downloadable artifacts (.docx, .xlsx, .pptx, .png, .html). The rebuild targets a single-user deployment, which materially simplifies the platform: billing, plan enforcement, and tenant isolation collapse into local accounting and a single-owner row-level security policy, while the interesting engineering — DAG execution, cascading re-runs, multi-tier agent orchestration, and multi-provider model routing — is preserved in full.

### 1.1 What is being rebuilt
* An infinite canvas workspace where every artifact is a typed block, and every dependency is an explicit edge.
* A run engine that accepts a natural-language prompt plus constraints and materialises a block graph as output, tracking status, estimated_duration_ms, and credits_consumed per run.
* A block library spanning 17 API-addressable block types plus 5 app-only container/UI block types (Chat, Frames, Inputs, Folder, Folder Synthesis).
* Swarm Mode: a hierarchical task tree (tier / persona / agent_tier / parent_task_id) where an L1 conversational orchestrator plans, and lower tiers create and fill blocks.
* A cascading re-run engine: when an upstream block's content changes, descendants are invalidated and re-queued via topological traversal of the edges table plus Supabase Realtime postgres_changes subscriptions.
* An outbound integration and MCP layer: OAuth connectors persisted in an integrations table, plus a first-party MCP server built on the official TypeScript SDK.

### 1.2 What is deliberately out of scope
* Multi-tenant billing, subscription webhooks, and plan upgrade flows.
* Team/workspace sharing, roles, and invitations. RLS is a single-owner predicate.
* Horizontal worker fleets. Long-running block generation uses Vercel serverless/background functions with a Postgres-backed queue rather than a dedicated worker cluster.

Critical grounding caveat: every row in the proposed Postgres schema research table is flagged confidence = Inferred, derived from the public canvases-and-runs API concepts documentation rather than from the production DDL. Validate column names against live API payloads during Phase 1 before writing migrations that are expensive to reverse.

## 2. System Architecture

### 2.1 Layer Decomposition
The system is a single Next.js 14 App Router application deployed to Vercel, with Supabase providing authentication, Postgres, object storage, and realtime change streams. All server-side work is expressed as route handlers under app/api.

**TABLE 1 — ARCHITECTURAL LAYERS AND RESPONSIBILITIES**

| Layer | Implementation | Responsibilities |
| :--- | :--- | :--- |
| Canvas client | React 18 + @xyflow/react + Zustand + Tailwind | Infinite canvas rendering, node/edge editing, optimistic status badges, drag-to-connect, frame grouping |
| Realtime sync | Supabase Realtime (postgres_changes on blocks, runs, tasks) | Push block status transitions and content updates to the canvas; trigger downstream invalidation UI |
| API surface | Next.js App Router route handlers (app/api/**) | Run creation, block CRUD, artifact signing, webhook dispatch, MCP transport endpoint |
| Orchestration | Swarm planner + task dispatcher (Node runtime) | Decompose prompts into tasks, enforce allowed_block_types, topologically schedule work |
| Model router | Vercel AI SDK provider registry | Route each block type + agent tier to OpenAI / Anthropic / Google / OpenRouter with fallback |
| Generation workers | Serverless + background functions | Per-block-type generators (docx, xlsx, pptx, image, html, research) writing to Supabase Storage |
| Data | Supabase Postgres (12 tables) + Storage buckets | Canonical graph state, run history, artifacts, OAuth tokens, webhook delivery log |
| Integrations | MCP server + OAuth connectors | GitHub, Google Workspace, web, and YouTube ingress/egress |

### 2.2 Run Lifecycle
1. Intake. A run is created against a canvas with prompt, optional template, allowed_block_types, and agent_instructions; status is set to queued and estimated_duration_ms is written from a per-block-type cost model.
2. Planning. The Swarm planner writes rows to tasks, each carrying tier, persona, agent_tier, goal, and an optional parent_task_id to form the task tree.
3. Materialisation. Each leaf task creates a blocks row with status = pending and a position, then links it to its context sources via edges.
4. Execution. The dispatcher walks the DAG in topological order, flipping each block to running, invoking the block-type generator, and persisting content / url plus any file rows or run_artifacts rows.
5. Completion. Each block resolves to completed or failed; when all tasks resolve, the run records final_output, credits_consumed, and completed_at.
6. Propagation. Supabase Realtime broadcasts row changes to the canvas; webhook_deliveries rows are enqueued for every subscribed event on the user's webhook_endpoints.

Every AI-generating block type shares a single four-state machine — pending, running, completed, failed. Static container blocks (Frames, Inputs, Folder) have no generation lifecycle and render in a static state.

Design rule: the blocks table is the single source of truth for canvas state. The client never holds authoritative graph state; it holds a Zustand projection of Postgres rows kept fresh by Realtime.
